# Return focus when an overlay closes

- ID: a11y-8
- Category: Accessibility & inclusivity
- Tags: Accessibility, WCAG, Keyboard, Overlays
- URL: https://axiomui.nischal.fyi/rules/a11y-8

When an overlay closes, return keyboard focus to the control that opened it. If closing removes that control, such as when a row is deleted, focus the next logical control in the workflow.

- Do: Esc → focus back on "Edit"
- Don't: Esc, then Tab → focus restarts at "New project"

## Why it works

After closing the edit dialog for Quarterly report, someone using a keyboard is still working in that project row. Returning focus to Edit keeps their place so they can continue through the project list.

- [WAI-ARIA APG · Modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)
- [WCAG 2.2 · Focus order](https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html)

## What breaks

If focus falls back to the page body, the next Tab can land on New project at the top and make the user search for the row again.

## How to apply it

1. Use the overlay primitive’s focus restoration if it provides it. For custom overlays, remember the opener and restore focus after the background is available again.
2. Inspect document.activeElement after Escape, cancel and save. A body result or a jump to the first page control on the next Tab can reveal dropped focus.
3. If saving or deleting removes the opener, focus an action in the next row once the list updates. If no row remains, use a stable control such as New project.

## Review questions

1. Tab to Edit for Quarterly report, press Enter, then Esc. Is the focus outline back on Edit before you press Tab again?
2. Do Cancel and Save also put focus where the task should continue?
3. Delete the row from the dialog. Does focus land on the next logical control after the row disappears?
